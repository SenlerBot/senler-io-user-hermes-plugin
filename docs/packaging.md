# Формат, оформление и публикация

Пакет использует нативный формат Hermes: корневой `plugin.yaml` с
`manifest_version: 2` и точку входа `__init__.py`. Функция `register(ctx)`
регистрирует действия `senler_connect` и `senler_relay`, два skill, CLI-команду `senler` и платформу
`senler-io` через API плагинов.
Импорт и включение плагина не запускают вход и не изменяют MCP-настройки.

`mcp-server.json` — собственный файл настроек этого плагина: имя MCP, HTTPS-адрес,
OAuth и таймаут подключения. В интерактивном чате `senler_connect` подготавливает
отсутствующее подключение через штатный загрузчик и writer конфигурации Hermes.
Проверка имени и запись выполняются под его `_CONFIG_LOCK`; профиль определяется
при каждом вызове из текущего контекста Hermes. Существующая совместимая запись
не переписывается. Конфликт, повреждённый файл или запрет записи дают ошибку.
Необработанные ошибки конфигурации не попадают в чат: они могут содержать секреты.

Действие возвращает следующий вызов `manage_connections` с `action: authorize`
и `mcp: true` для `senler-io-user`. Для выключенного MCP сначала используется
штатное действие `enable`. Skill выполняет эти вызовы по очереди и прекращает
последовательность при отмене или сбое. OAuth, карточка, повторное использование
сохранённой авторизации и обнаружение инструментов принадлежат Hermes. Подготовка
настроек не считается успешным подключением. Плагин не вызывает OAuth подпроцессом
из чата, не читает токены и не запускает модель для проверки.

Подготовка разрешена только при нативном `connection_surface() == CARD`;
подзадачи, фоновые задания и контекст Relay отклоняются до записи. Если инструмент
Hermes `manage_connections` скрыт настройками или недоступен в сессии, skill направляет
пользователя к уже подготовленному серверу в интерфейсе Desktop и кнопке Authorize.

Для терминала `hermes senler connect` читает те же настройки и вызывает штатные MCP-команды
Hermes в том же Python и профиле. Hermes выполняет вход, хранит токены и
сохраняет подключение.
Существующее совместимое подключение проверяется без замены настроек.
Hermes может запросить вход, если сохранённая авторизация больше не работает;
`--reauthorize` принудительно запускает новый вход через штатную команду Hermes.

## Логотип

`assets/icon.svg` — точная копия `aibot-cabinet/public/senler-logo.svg`, исходного
логотипа кабинета Senler.io. Из этого SVG кабинет получает `favicon.png`, который
показывается в его боковой панели. Цвет — `#00ADFF`. README использует относительную ссылку,
чтобы изображение работало в распакованном пакете и в GitHub-репозитории.
Установщик сохраняет каталог `assets` вместе с README.

Для картинки карточки официального каталога Hermes используется `image` в
отдельной записи `plugin-catalog/<name>.yaml` репозитория Hermes.
`assets/catalog-banner.svg` — баннер 1200×600 (2:1) с тем же SVG-контуром и цветом
логотипа кабинета. Его PNG-копия предназначена для карточки каталога и README.
При изменении SVG нужно обновлять PNG из этого же файла. HTTPS-ссылка на картинку
закрепляется на том же полном commit SHA, что и запись каталога.
Квадратный `assets/icon.svg` сохранён как исходный логотип.
Исходники публикуются в [SenlerBot/senler-io-user-hermes-plugin](https://github.com/SenlerBot/senler-io-user-hermes-plugin),
тестовые выпуски — в GitHub Releases. [Первоначальная заявка в каталог](https://github.com/NousResearch/hermes-agent/pull/136761)
принята 12 октября 2026 года. Установка из GitHub выполняется напрямую по README;
каталог использует отдельно проверенный commit SHA.

Для заявки подготовлены английские описание, начало README и сведения о сетевых
подключениях, фоновом выполнении, локальном хранении данных и полномочиях
`trusted_inbound`. Пользователь подтвердил установку и вход из чата в Windows
Desktop. Это не подтверждение обработки настоящего события Relay.

Заявка изменяет только `plugin-catalog/senler-io-user.yaml` в репозитории Hermes.
Исходники остаются в репозитории Senler; версия и полный SHA фиксируют проверенный
код. Публикация карточки и смена SHA требуют принятия PR сопровождающими Hermes.
Перед подачей выполняются `hermes plugins validate <path> --install-deps` и
официальный структурный валидатор записи каталога. Первоначальная заявка фиксировала
runtime 0.4.1 с оформлением для каталога и не меняла опубликованный тег v0.4.1.

Для первоначальной подачи использовался полный валидатор Hermes commit
`0d3b11c21c57c4d66f6719d7036904ea1056841c` в отдельном профиле и окружении,
подготовленном штатным PM по его зафиксированным зависимостям (Python 3.14.7).
Проверки включают импорт и регистрацию, зависимости, совпадение возможностей,
Plugin Guard, отсутствие подмены функций ядра, Desktop surface и проверку
поставляемых файлов на исполняемые бинарные вложения. Сетевой вход в Senler
и вызовы модели эти проверки не выполняют.

## Границы проверки

Изменения 0.5.0 добавляют управление подпиской из чата, штатный поиск отложенных
MCP-инструментов и очередь уведомлений. Очередь сохраняется атомарно с итогом
обработки. Получатель задаётся оператором; его смена отменяет ожидающую доставку
старому адресату. Модель возвращает решение о важности и краткий текст. Отправку
выполняют штатные `gateway.delivery.resolve_delivery_transport` и
`DeliveryTransport.send`, без дополнительного вызова модели. Неопределённый исход
отправки требует ручной проверки; повторяются заведомо не начатая отправка и явный
rate limit. Общий инструмент отправки фоновой модели не предоставляется.

`ctx.inject_message` не используется: он запускает новый ход модели, а его `True`
подтверждает только приём запроса. Произвольные чаты Desktop/TUI требуют другого
публичного механизма доставки; их `origin` отклоняется до сохранения настройки.
Разрешения Hermes не отключаются.

SQLite расширяется таблицами очереди, квитанций и состояния Relay. Прежние подписки
продолжают работать без уведомлений. Локальный получатель исключён из серверного
контракта и сохраняется при обновлении ключа/типов событий. Тесты проверяют запись
через обработчик нативного инструмента. Статус соединения отражает свежий управляющий
пакет. Проверка доставки имеет отдельный ID и требует квитанции адаптера.

`tests/native_monitor_probe.py --source-dir <исходники-Hermes>` проверяет штатные
поиск и описание инструментов, распаковку `tool_call`, ограничения фонового вызова
и доставку через `DeliveryTransport` с настоящим `SendResult`. Подменяются каталог
тестового MCP и внешний отправитель; ни OAuth, ни модель, ни реальные сообщения не
вызываются. Ключевые функции доставки и проверки вызова сверены с Hermes
`e3c3d273901894ea98aee33f1fa20f3b460ba2dc`; они совпадают с полным окружением
`0d3b11c21c57c4d66f6719d7036904ea1056841c`, используемым для нативной проверки.

Формат и API регистрации сверены с официальной схемой и исходниками Hermes на
коммите `0d3b0348f5aab2bc263c81b660d761a76ded14fe` от проверки 10 октября 2026.
Проба из `hermes_cli/plugin_validate.py` импортирует пакет и вызывает `register`
в отдельном процессе с записывающим контекстом. Полная команда
`hermes plugins validate <path>` запускается установщиком в пользовательском
Hermes до копирования файлов. Локальные PowerShell-тесты заменяют CLI тестовой
командой; это не запуск полноценного Hermes.

Это проверка формата и локальной установки, а не подтверждение работы OAuth,
отображения в конкретной версии Desktop или обработки реального вебхука.
Сквозная проверка выполняется по [windows-test.md](windows-test.md).

## Hermes Relay 0.4

Платформа `senler-io` регистрируется через `register_platform`, адаптер использует
`gateway.relay.ws_transport.WebSocketRelayTransport`. Проверяемый контракт:
[Hermes Relay](https://hermes-agent.nousresearch.com/docs/developer-guide/relay-connector-contract/),
исходники commit `0d3b0348f5aab2bc263c81b660d761a76ded14fe`. Протокол Relay
экспериментальный; отсутствие этих API требует обновления Hermes. Плагин
регистрирует публичный hook `pre_tool_call`: он проверяет сохранённое состояние
конкретной попытки и подставляет ключ повторной отправки одного ответа.
Неизменяемая привязка к событию передаётся через `ContextVar` при запуске задания;
нативные gateway, tool workers и hooks Hermes переносят этот контекст в свои потоки.
Публичный `on_session_end` передаёт признаки завершения, ошибки и прерывания
в ту же попытку через потокобезопасное одноразовое подтверждение. Итог фиксируется
после окончания доставки отчёта gateway: успешная доставка текста ошибки сама
по себе не означает успешную обработку. Если уведомления или обязательных признаков
нет, сохраняется ошибка с пояснением; позднее уведомление её не переписывает.
В проверенных исходниках ранний возврат из цикла модели может обойти финализатор,
поэтому ожидание уведомления отдельно не продлевает работу задания.
Обычные чаты пользователя hooks не изменяют. Регистрация
плагина не открывает сеть и не создаёт локальную базу. Работающий gateway
создаёт `senler-io-relay.sqlite3` внутри своего Hermes home: настройки scoped
подключений, ограниченную очередь и отчёты. Файл содержит ключи — не публикуйте его.

Адаптер подтверждает приём текста отчёта только после записи в поле `inbox.result`
активной попытки; состояние остаётся `processing`. Привязка к попытке берётся из
того же `ContextVar`, отдельного буфера текста в памяти нет. Запись текста и
завершение при паузе, смене настроек или восстановлении сериализуются транзакциями
SQLite. Завершение читает сохранённый текст, добавляет причину ошибки перед ним
и переводит запись в `done`; только тогда результат отправляется в Senler.
Поздняя запись закрытой или заменённой попытки отклоняется. Итог ограничен
16 000 символами, причина ошибки сохраняется при усечении.

Адаптер объявляет `SUPPORTS_MESSAGE_EDITING = False`: штатный gateway передаёт
завершённые сообщения без промежуточных токенов и курсора, даже если пользователь
включил глобальный потоковый вывод. Завершённые промежуточные сообщения сохраняются
в отчёте и остаются доступны при прерывании. Глобальные настройки Hermes не меняются.

Настройка, возобновление подписки и запуск адаптера проверяют режим gateway.
`gateway.proxy_url` и профильный `GATEWAY_PROXY_URL` означают выполнение агента
в другом Hermes, куда текущий контракт не передаёт контекст попытки Senler.
В таком режиме включение входящих отклоняется с объяснением; облачный провайдер
модели сам по себе ограничением не является. Переменная окружения используется
только при отсутствии профильного secret scope, как в проверенном gateway Hermes.
Та же проверка выполняется до запроса `senler_start`, после его ответа и на входе
в обработчик Hermes. До локального начала выполнения событие остаётся ожидающим
с прежним ID попытки; повторный запрос разрешения использует этот ID. После
локального начала отказ обработчика завершает попытку с ошибкой, без повтора действий.
Несовместимость не меняет настройки подписок и не останавливает отправку готовых
отчётов или истечение срока ожидания. Исправление настройки автоматически допускает
ожидающие события, если подписка не на ручной паузе. Причина записывается в лог
только при изменении состояния и вычисляется из текущих настроек при `relay status`
в поле `processing_blocked_reason`; `null` означает отсутствие этой несовместимости,
но не подтверждает, что gateway запущен. Место выполнения агента следует менять
с остановкой и последующим запуском gateway: безопасного переноса начатой задачи нет.

Вход в адаптер допускает только текущее событие локальной очереди с активной
попыткой. Штатное восстановление сессий Hermes не может повторно запустить
прерванное событие. При завершении право на новые действия и запись отчёта
отзывается в памяти до обращения к SQLite. Если итог не удалось сохранить,
отмена gateway всё равно выполняется; единственный обработчик очереди повторяет
только запись итога, не переходя к следующему событию. При выключении gateway
повторы прекращаются, незавершённую запись закроет восстановление при запуске.

На локальной паузе соединение открывается только для ожидающего отправки отчёта,
без обработчика входящих событий. После hello плагин вызывает штатный `go_idle`
и ждёт `going_idle_ack`: Senler прекращает доставку событий и проверочных проб
на этом соединении, сохраняя очередь на сервере. Затем плагин отправляет отчёт
и закрывает соединение после подтверждения. Неуспешная доставка повторяется
с новым подтверждением режима паузы; задания модели не запускаются. Продолжение
обработки требует обычного соединения с проверками подписки.

Подключение выполняется отдельно для каждой подписки: не более восьми задач
на профиль и одной задачи на подписку, с таймаутом 15 секунд на соединение и
15 секунд на hello. Отправка готовых отчётов по рабочим соединениям продолжается
независимо, с прежним бюджетом пять секунд на проход. Задача подключения на паузе
отправляет один сохранённый отчёт с собственным пятисекундным таймаутом и закрывается.
Следующая попытка выбирает следующий отчёт, чтобы отказ по старому не задерживал новые.
Изменение настроек отменяет устаревшую попытку; новое подключение ждёт завершения
её очистки. Выключение gateway дожидается закрытия всех принадлежащих ему задач и соединений.

Тесты транспорта, хранилища и установщика не заменяют ручную проверку OAuth
и выполнения задания в настоящем Hermes на Windows. Серверные изменения
Senler API/User MCP должны быть развёрнуты отдельно от установки плагина.

Локальные проверки пакета:

```powershell
python -m unittest discover -s tests -p "test_*.py"
powershell -NoProfile -ExecutionPolicy Bypass -File tests/install.Tests.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File tests/run-relay.Tests.ps1
```

`tests/native_relay_probe.py --source-dir <каталог-исходников-relay>` проверяет
неизменённый `WebSocketRelayTransport` указанного выше коммита против тестового
коннектора. В каталоге нужны `ws_transport.py`, `auth.py`, `descriptor.py`,
`event.py`; в Python — пакет `websockets`. Тест подменяет только реестр платформ
и структуру источника сессии, не запускает gateway или модель. Проверяются
рукопожатие, NDJSON, подтверждение после записи события, разрешение начала обработки
и возврат результата, а также `going_idle`/`going_idle_ack` и доставку отчёта
без подтверждения входящих событий на паузе.

`tests/native_hook_probe.py --source-dir <каталог-исходников-Hermes>` проверяет
запрет восстановления прерванного события через `gateway/run_startup.py` и
`gateway/platforms/base.py`, отказ во входе при смене режима gateway и допуск после
его исправления, затем привязку попытки через исходный метод executor gateway, `tools/thread_context.py`
и `hermes_cli/plugins_dispatch.py` того же коммита. Старое задание задерживается,
отменяется через паузу, затем продолжает работу одновременно с новым: его вызов
блокируется, новое задание получает собственный ключ и результат своего `on_session_end`.
Текст отчёта проходит обратно из рабочего потока в event loop и сохраняется в SQLite;
запоздавшие завершение и текст старого задания не меняют результат нового. Обычный чат сохраняет своё
поведение. Модель и MCP не вызываются; сервисы конфигурации и терминальных запросов
подменены, метод executor загружается отдельно от полного gateway.

`tests/native_stream_probe.py --source-dir <каталог-исходников-Hermes>` использует
исходные `_setup_stream_consumer`, `_build_stream_consumer_config` и
`GatewayStreamConsumer` того же коммита. При включённом потоковом выводе проверяются
единственная доставка итогового текста и сохранение завершённого промежуточного
сообщения при прерывании. Модель не запускается; медиа и служебные зависимости
подменены для коротких текстовых ответов. Нужны исходники `gateway/stream_consumer*.py`,
`gateway/run_turn*.py`, `gateway/response_filters.py`, `gateway/platforms/base.py`,
`gateway/platforms/helpers.py`, `gateway/relay/egress.py` и `agent/think_scrubber.py`.
